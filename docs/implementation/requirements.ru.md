# Промпт для GPT Astra 6: Meetily с обнаружением звонков, CLI и MCP

Ты работаешь как инженер в облачном окружении над нашим GitHub-форком Meetily Community Edition.

Upstream: https://github.com/Zackriya-Solutions/meetily

Сделай работающую реализацию, тесты, сборки и документацию. Результат нужен для повседневного использования на macOS и Windows. Промпт разрешает изменения в предоставленном форке и подготовку draft PR внутри него. Публикация релизов, merge и изменения upstream не входят в задачу. Если доступ на запись отсутствует, сохрани изменения и сообщи конкретное ограничение.

## 1. Цель и пользовательский сценарий

Meetily обнаруживает, что пользователь вошёл в звонок Zoom или Discord, и показывает уведомление «Обнаружен звонок» с действиями «Начать запись» и «Пропустить». Запись начинается только после нажатия пользователя. Обнаружение звонка само по себе никогда не включает запись.

Приложение записывает микрофон и системный звук, локально распознаёт речь и сохраняет встречу. Пользователь может получить транскрипт через MCP в локальном Codex и попросить Codex сделать конспект, решения, задачи и открытые вопросы. Подключение OpenAI API и встроенная локальная суммаризация для этого сценария не требуются.

CLI — инструмент управления и диагностики. MCP и CLI должны использовать ту же запись и хранилище, что интерфейс приложения. Они не создают собственный независимый аудиорекордер.

Обязательные платформы первого выпуска:

- macOS Apple Silicon. Конкретная машина пользователя: macOS 14.8.5; она должна поддерживаться.
- Windows 10/11 x64. Установи точный минимальный поддерживаемый build по реально используемым API и зависимостям и задокументируй его.

Zoom и Discord desktop обязательны на обеих платформах. Microsoft Teams desktop добавь следующим адаптером, если техническая возможность подтверждена; для прочих приложений нужен расширяемый интерфейс адаптеров и честная таблица возможностей. Браузерные Google Meet/Teams/Zoom — отдельный режим эвристического обнаружения, если доступны достаточные сигналы. Активный микрофон браузера сам по себе не означает звонок в конкретном сервисе.

## 2. Сначала проверь исходники и зафиксируй основание

Работай от актуальной default branch предоставленного форка. Запиши upstream URL, base commit SHA, версии инструментария и исходный результат сборки/тестов. Если форк отсутствует, явно сообщи, что нужен репозиторий с правом записи; не выдавай upstream за наш форк.

Предварительно исследована Community 0.4.1. Проверяй все выводы на своём checkout. В ней полезны следующие точки входа:

- `frontend/src-tauri/src/lib.rs` и `src/main.rs` — запуск Tauri и команды.
- `frontend/src-tauri/src/audio/recording_commands.rs`, `recording_manager.rs` — жизненный цикл записи.
- `frontend/src-tauri/src/audio/capture/` — системный звук и различия платформ.
- `frontend/src-tauri/src/tray.rs` — управление через значок приложения.
- `frontend/src/hooks/useRecordingStart.ts`, `useRecordingStop.ts`, `frontend/src/services/recordingService.ts` — часть жизненного цикла в интерфейсе.
- `frontend/src-tauri/src/database/repositories/transcript.rs` — сохранение встречи и транскриптов.
- `frontend/src/components/LanguageSelection.tsx`, `src/contexts/ConfigContext.tsx` — язык распознавания.
- `.github/workflows/build-macos.yml`, `build-windows.yml`, `build.yml` — существующие сборки.

Особенно проверь зависимость сохранения встречи и транскриптов от React-событий после остановки. Для CLI/MCP/скрытого окна backend должен самостоятельно завершать и сохранять встречу. Успешный вызов `stop_recording` ещё не означает, что весь текст сохранён.

Текущий поддерживаемый путь — Tauri desktop. Исторический `backend/` с FastAPI не используй как основание нового сервера.

Сохрани MIT-лицензию и необходимые уведомления из Community. Реализуй функции самостоятельно на основе публичных исходников и API. Код закрытой Pro Edition не является исходным материалом задачи.

## 3. Архитектура и порядок реализации

Используй существующие Rust/Tauri, React/TypeScript, аудиодвижки и базу данных. Сначала составь короткий план в репозитории, затем реализуй его без остановки после одного проектирования. Рутинные технические решения принимай самостоятельно; существенные несовместимости обозначай явно.

Раздели работу на последовательные этапы:

1. Общий backend-сервис записи, состояния и надёжного сохранения.
2. Локальный интерфейс управления, CLI и MCP.
3. Общий механизм обнаружения звонков и реальные адаптеры macOS/Windows.
4. Настройки, уведомления, упаковка и проверка обеих платформ.

Все вызывающие стороны — GUI, tray, уведомления, CLI и MCP — обращаются к одному сервису. Сериализуй start/stop и изменения состояния. Возвращай `recording_id`, `meeting_id`, инициатора записи и типизированные ошибки. Повторный start не создаёт вторую запись; повторный stop возвращает понятное уже завершённое состояние.

Разделяй прекращение захвата аудио и окончание обработки транскрипта. При остановке дождись оставшихся сегментов, транзакционно сохрани встречу и только затем публикуй `meeting.finalized`. Сохраняй промежуточный результат так, чтобы сбой приложения не терял всю встречу; незавершённые встречи должны иметь явно обозначенное состояние.

Работа должна продолжаться при скрытом окне или нахождении GUI на другой странице. Закрытие в tray и выход из приложения различай. После аварийного рестарта приложение не начинает запись автоматически.

## 4. Обнаружение звонков

Обнаружение открытого процесса — только один сигнал. Запущенный Zoom без встречи, открытый Discord с текстовым чатом, проигрывание видео и тест микрофона не должны называться подтверждённым звонком.

Реализуй общий интерфейс наблюдателя/адаптера. Он возвращает приложение, идентификатор наблюдаемой сессии, состояние, доказательства обнаружения, уровень уверенности, ограничения и время наблюдения. Представляй `unknown` и `unsupported` отдельно от `no_call`.

Для macOS исследуй публичные Core Audio API: связь аудиопроцессов с PID/bundle ID, состояние input/output и события изменения. Проверь availability API для macOS 14.8.5. Для Windows исследуй Core Audio/WASAPI: аудиосессии, PID, состояние сессий и уведомления устройств. Учти дочерние процессы Electron и Zoom, многопроцессные аудиосессии, смену устройств и PID reuse.

Эти API дают сигналы активности аудио, а не универсальный факт участия в звонке. Если для Zoom/Discord нужны дополнительные признаки состояния звонка, используй публичные возможности приложения или ограниченный адаптер Accessibility/UI Automation. Запрашивай необходимые разрешения с понятным объяснением. Отсутствие разрешения должно приводить к явному ухудшению возможностей, а не фиктивному успешному обнаружению.

Предпочитай системные события. Небольшой ограниченный polling допустим там, где подходящих событий нет; укажи причину, интервал и ожидаемую нагрузку. Нужен реальный native-код на обеих ОС, а не только mock-адаптеры.

Раздели состояния обнаружения звонка и записи. Добавь debounce, grace period и подавление повторных уведомлений. «Пропустить» или закрытое уведомление подавляет предложение до окончания этой сессии. Ручная остановка также не должна немедленно повторять предложение для того же звонка.

Молчание, mute, deafen, краткое переподключение и смена аудиоустройства не означают окончание встречи. После подтверждённого выхода предложи «Завершить и сохранить». Автоостановку сделай отдельной отключённой по умолчанию настройкой; она действует только на запись, связанную с этой обнаруженной сессией. Детектор не останавливает независимую ручную или CLI/MCP-запись. Одновременные признаки нескольких приложений не создают несколько записей.

Предложенные исходные интервалы: debounce 3 секунды, grace period 20 секунд. Сделай их настройками и проверь на тестовых последовательностях; при необходимости обоснуй корректировку.

## 5. Пользовательский интерфейс

Добавь настройки обнаружения звонков, список поддерживаемых приложений, режим уведомлений, автоостановку и запуск при входе в ОС. Запуск при входе включается пользователем и запускает наблюдение, а не запись. Детектор должен работать в tray, пока приложение запущено; при полном выходе наблюдение прекращается.

Уведомление содержит название приложения и действия начала записи/пропуска. Если системные action buttons недоступны, клик открывает компактное окно с теми же действиями. На Windows реализуй штатную активацию уведомления для упакованного приложения. Проверь, что действие обращается к текущей сессии: запоздалое нажатие после конца звонка не включает запись.

Добавь видимое состояние записи, индикаторы микрофона/системного звука и диагностику разрешений, устройств и моделей. Пользовательские тексты объясняют действие без технического жаргона.

Не заставляй скачивать Summary Engine или запускать LLM для использования транскрибации/MCP. Сохрани оба движка распознавания. Для русского с фиксированным языком используй Whisper с `ru`; Parakeet явно показывай как автоопределение. Настройки движка, языка и устройств должны читаться backend без запуска страницы React.

Системный звук может включать звук всего компьютера. Показывай фактический режим захвата и не называй его изолированным звуком Zoom, если такой изоляции нет.

## 6. CLI и локальное управление

Добавь отдельный небольшой бинарник `meetilyctl`, собираемый для обеих платформ. Он обращается к работающему приложению. При закрытом приложении возвращает диагностируемую ошибку; запуск приложения по команде можно реализовать явно, но не скрыто в любой read-команде.

Контракт команд:

```text
meetilyctl doctor --json
meetilyctl status --json
meetilyctl devices list --json
meetilyctl recording start --name "Zoom meeting" --language ru
meetilyctl recording stop
meetilyctl recording pause
meetilyctl recording resume
meetilyctl recording wait --until finalized --timeout 120
meetilyctl meetings list --limit 20 --json
meetilyctl meetings get <id> --json
meetilyctl meetings export <id> --format md|txt|json
meetilyctl transcript get <id> --cursor <cursor> --limit 200 --json
meetilyctl watch --events recording.started,recording.stopped,meeting.finalized --json
meetilyctl mcp serve
```

`--language` использует тот же механизм, что GUI; несовместимый движок возвращает понятную ошибку. Для записи предусмотрены выбор устройств и idempotency key. `wait` должен уточнять, какой `recording_id`/`meeting_id` ожидает, и иметь конечный timeout. `watch` выдаёт NDJSON-события с ID, временем и идентификатором встречи, поддерживает отмену и переподключение без дублирования.

Общий локальный gateway сделай версионированным. Можно использовать аутентифицированный loopback HTTP/SSE; слушай только loopback и проверяй доступ для каждого запроса. Запросы с произвольной веб-страницы не получают доступа. Интеграции включаются пользователем. Раздели права чтения и управления записью; ключи должны отзываться. Используй файл ключа или защищённое хранилище ОС, не аргумент с секретом в командной строке. CLI/MCP не читают SQLite напрямую и не обходят слой управления.

Укажи стабильные exit codes. JSON-результаты машинно читаемы; логи идут в stderr. Пагинация не обрезает данные молча. Время выдавай в ISO 8601 с UTC/offset, аудиопозиции — отдельно в секундах.

## 7. MCP для локального Codex

Реализуй стандартный MCP server по stdio в `meetilyctl mcp serve` через поддерживаемый SDK. stdout содержит только сообщения протокола; диагностика идёт в stderr. Сервер использует общий gateway и работает с локальным экземпляром Meetily, а не с облачным Mac/Windows пользователя.

Минимальные инструменты:

- `list_meetings` — фильтры, порядок, пагинация и состояние готовности.
- `get_meeting` — метаданные, источник звонка и статус обработки.
- `get_transcript` — сегменты с временными метками, cursor и признак частичного результата.
- `search_transcripts` — запрос и фрагменты с ID встречи/временными метками.
- `export_meeting` — Markdown/text/JSON как результат, без произвольной записи файлов.
- `get_recording_status` и `get_detection_status`.
- `start_recording` и `stop_recording` — доступны только при отдельно разрешённом управлении записью.
- `save_summary` — необязательный инструмент с отдельным правом записи: сохранить подготовленный Codex конспект без обращения к LLM. Существующий конспект заменяется только с явным параметром подтверждения.

По умолчанию MCP читает данные. Подключение MCP само по себе не разрешает запись аудио. Инструменты возвращают типизированные ошибки и корректные MCP annotations. Отмена и таймаут MCP-запроса не должны тайно останавливать запись или запускать новую.

Пользовательская фраза «Суммаризируй последнюю встречу» должна быть выполнима через `list_meetings` и `get_transcript`. Встречу выбирай по явно возвращаемой дате и состоянию, а не случайному порядку SQLite. Сохраняй метки времени и неизвестных спикеров; распознавание личности и новая диаризация в эту задачу не входят.

Подготовь проверенные команды подключения и примеры конфигурации Codex для macOS и Windows с абсолютным путём к бинарнику. Конфигурацию пользователя автоматически не перезаписывай. Добавь пример запроса на конспект и опиши передачу текста встречи в выбранный пользователем AI-сервис.

## 8. Тесты и сборки

Раздели проверяемый общий код и native API. В облаке запускай настоящие unit/integration tests, CLI-тесты и MCP protocol smoke test с реальным SDK-клиентом. Mock-адаптеры пригодны для общей логики, но не доказывают обнаружение реального звонка.

Обязательные тестовые сценарии:

- Открытый Zoom без встречи и Discord только с текстовым чатом.
- Начало/конец звонка, mute/deafen, молчание и переподключение.
- Нажатие «Пропустить», ручная остановка и запоздалое действие уведомления.
- Смена устройства, сон/пробуждение, завершение дочернего процесса, две конференционные программы.
- Нет разрешений или модели; выключены интеграции; неверный/отозванный ключ.
- Одновременные start/stop через GUI/CLI/MCP; отсутствие дублирующих встреч.
- Скрытое окно, оставшиеся сегменты после stop, аварийный рестарт и восстановление частичной встречи.
- Полная выгрузка большого транскрипта с пагинацией и сохранением порядка.
- MCP initialize/tools/list/tools/call и чистый протокольный stdout.

Добавь CI на macOS и Windows: native compilation, релевантные тесты, сборка desktop-приложения и CLI. Не ограничивайся Linux-тестами или `cargo check` только общего mock-кода. Сохрани существующую поддержку других ОС там, где она была; детектор на неподдерживаемой ОС возвращает `unsupported`.

Подготовь устанавливаемые тестовые артефакты для обеих ОС. Подпись/нотаризация проверяется отдельно; если секретов нет, не выдавай unsigned build за подписанный. Отдели название/идентификатор форка и канал обновлений от upstream. Тестовая установка не должна перезаписывать существующее приложение, базу или модели пользователя. Для переноса данных используй явный импорт с резервной копией и проверкой версии, а не работу двух приложений с одной базой.

## 9. Критерии приёмки и итог

Доведи код до состояния, которое можно собрать и проверить локально. Подготовь draft PR в нашем форке, если это доступно. В PR и итоговом отчёте укажи:

1. Реализованные возможности и архитектуру с точными путями.
2. Base SHA, commit SHA и результаты каждой реально выполненной проверки.
3. Ссылки на CI и артефакты macOS/Windows, либо точные команды сборки и конкретный блокер.
4. Матрицу обнаружения: приложение/ОС/сигналы/ограничения/уровень проверки.
5. Инструкцию установки, подключения MCP в Codex и использования CLI.
6. Короткий пошаговый план проверки реальных Zoom/Discord на обеих ОС, включая вход с выключенным микрофоном и звук собеседника в наушниках.

Различай: написано, собрано, проверено на mock, проверено протокольным клиентом, проверено на реальном звонке. Облако без интерактивных macOS/Windows и аудио не подтверждает работу реальных звонков. В таком случае предоставь native-код, CI-сборки и воспроизводимый локальный тест, а этот пункт приёмки отметь как ожидающий проверки.

Задача не завершается архитектурным описанием, заглушками детектора или одним MCP-сервером. Оба desktop-приложения, общий жизненный цикл записи, CLI, MCP, уведомления и реальные платформенные адаптеры должны быть реализованы; каждый недоступный этап проверки должен иметь конкретную причину.
